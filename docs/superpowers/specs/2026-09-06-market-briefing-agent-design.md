# 마켓브리핑 온디맨드 대시보드 에이전트 설계

작성일: 2026-09-06
상태: 승인됨 (구현 계획 작성 대기)

## 배경

KECOBUGS 26th 마켓브리핑 작성을 돕기 위해 `market-briefing/`에 텔레그램 일일 수집
자동화(`telegram_digest.py` + Windows 작업 스케줄러 정오 실행)를 먼저 구축했다.
수집 자체는 동작하지만, 산출물이 채널별 원문을 그대로 쌓아둔 마크다운 파일이라
한눈에 파악이 어렵고, 그것을 에이전트가 채팅에 불릿으로 요약해주는 방식은
"구체적이지도 가시적이지도 않다"는 피드백을 받았다.

이 문서는 **사용자가 원할 때마다 호출하는 온디맨드 시황 브리핑 파이프라인**을
설계한다. 산출물은 채팅 텍스트가 아니라 차트가 포함된 대시보드 Artifact이며,
매 호출마다 같은 URL을 갱신한다.

## 결정 사항 (브레인스토밍 확정)

1. **산출물 = 차트/대시보드 형태의 시각 보고서** (텍스트 보고서 아님)
2. **지표 범위 = 고정 시장 개괄** — 코스피·코스닥·S&P500·나스닥·원/달러·美10년물·VIX
   (이슈별 동적 종목 차트는 v2 과제로 보류)
3. **전달 방식 = 단일 Artifact URL을 매번 갱신** (호출마다 새 링크 생성 아님)
4. **트리거 = 온디맨드** — 사용자가 "브리핑 줘" 등으로 호출할 때 실행. 텔레그램
   정오 수집은 배경에서 계속 돌며 원자재를 공급한다.
5. **아키텍처 = 파이썬 사전축약 + 토픽별 병렬 서브에이전트** (아래 비교 참조)

## 아키텍처 비교

| 방식 | 중복 제거 품질 | 비용/속도 | 판정 |
|---|---|---|---|
| A. 채널당 에이전트 1개 (37개 팬아웃) | **불가능** — 각자 자기 채널만 보므로 타 채널 중복을 인지 못 함 | 최악 (콜드스타트 37회) | 탈락 |
| B. 단계별 순차 에이전트 | 양호 | 느림 — 단계마다 원문 전체를 넘김 | 부분 채택 |
| C. 단일 에이전트 (오케스트레이터가 전부 수행) | 양호 | 매 호출마다 원문 70~140k 토큰 적재, 병렬화 없음 | 탈락 |
| **D. 파이썬 사전축약 + 토픽별 병렬 에이전트** | **최상** | **최적** | **채택** |

D안의 근거는 두 가지다.

- **중복 제거는 전역 시야가 필요한 작업**이다. 채널 단위로 쪼개면 원리적으로
  불가능하므로, 반드시 한 곳에서 전체를 한 번에 보는 단계가 있어야 한다.
- **그 전역 시야를 원문 전체가 아니라 축약 인덱스로 확보**하면 비용이 대폭 줄어든다.
  URL·티커·숫자·정규화 해시 기반의 고신뢰 중복 탐지는 결정적 연산이므로 파이썬이
  담당하고, LLM은 의미 수준의 병합 판단만 맡는다.

## 병합 규칙 — 토픽 단위 병합, 채널 단위 레이아웃

한 채널이 보통 여러 이슈를 동시에 다루므로 **채널 통째 병합은 성립하지 않는다**.
(예: 「급등일보 미국주식」은 이란 유조선 건(타 채널과 중복)과 PLTR 인터뷰(고유)를
같은 날 올린다.) 따라서:

- 병합은 **토픽 단위**로 수행하고, 각 토픽마다 primary 채널 하나를 지정한다.
- 보고서 레이아웃은 **채널 단위**를 유지한다.
- 토픽을 뺏긴 채널에는 병합 사실을 명시해 혼란을 막는다.

아래는 병합 표기법을 설명하기 위한 **예시 발췌**다 (2026-09-06 실제 수집분에서
중복이 발생한 두 채널만 잘라 온 것). 실제 보고서에는 그날 새 글이 있는 모든
채널의 섹션이 들어간다 — 같은 날 기준 8개 채널.

```
## 미국 주식 인사이더
[정리] 미국이 자국 군함 피격 대응으로 이란 유조선 3척 타격…
[요약] 호르무즈 통항 리스크가 실물 유가로 전이되는 구간
[지표] WTI $XX.X (+X.X%) · VIX XX.X
      ↳ 「급등일보 미국주식」의 동일 이슈가 이 섹션에 병합됨

## 급등일보 미국주식
→ 이란-미국 충돌 건은 「미국 주식 인사이더」 섹션으로 병합됨
[정리] PLTR 알렉스 카프 인터뷰 — 엔비디아 협업·전력 인프라 언급
```

## 파이프라인

```
사용자: "브리핑 줘"
  │
  ▼
[오케스트레이터 = 메인 세션]
  │
  ├─1. 수집 (파이썬)            telegram_digest.py → daily/YYYY-MM-DD.md
  │                              market_snapshot.py → market_snapshot.json
  ├─2. 사전축약·중복탐지 (파이썬) build_index.py    → briefing_index.json
  ├─3. 토픽 클러스터링 (오케스트레이터, 인덱스만 읽음) → topics.json
  ├─4. 토픽별 섹션 작성 (서브에이전트 N개, 병렬)      → sections/*.json
  ├─5. 검수 (섹션 6개 이상일 때만 서브에이전트)
  └─6. 렌더 (오케스트레이터) → 대시보드 Artifact 갱신 + 채팅 핵심 요약
```

### 단계별 실행 주체와 근거

| 단계 | 주체 | 근거 |
|---|---|---|
| 1. 수집 | 파이썬 | 판단 불필요한 결정적 작업. LLM 투입은 낭비 |
| 2. 사전축약·중복탐지 | 파이썬 | URL/해시 일치는 결정적 연산. 고신뢰 중복을 먼저 걷어내 LLM 입력을 줄임 |
| 3. 토픽 클러스터링 | 오케스트레이터 | 이후 모든 단계가 의존하는 축이므로 메인 컨텍스트에 있어야 조립·설명이 일관됨 |
| 4. 섹션 작성 | 서브에이전트 (병렬) | 토픽 간 독립적이라 진짜 병렬이 되고, 섹션당 웹 검색 2~5회의 출력을 메인 컨텍스트에서 격리 |
| 5. 검수 | 조건부 서브에이전트 | 섹션 작성자들은 서로를 못 보므로 잔여 중복 확인 필요. 섹션이 적으면 오케스트레이터가 겸함 |
| 6. 렌더 | 오케스트레이터 | Artifact 발행·갱신은 메인 세션 도구 |

섹션 작성 에이전트는 `model: sonnet`을 지정한다. 요약·검증 작업 특성상 품질 손실
없이 비용과 지연이 개선된다.

## 산출 파일

중간 산출물은 모두 `market-briefing/scripts/.state/` 아래에 둔다 (이미 `.gitignore`
등록됨 — 세션 파일·수집 원문과 같은 취급).

**파이썬 (결정적)**
- `market-briefing/scripts/market_snapshot.py` (신규) — 고정 지표 현재가·등락률·
  최근 3개월 종가 → `.state/market_snapshot.json`
- `market-briefing/scripts/build_index.py` (신규) — 다이제스트를 메시지 단위로 분해,
  URL·티커·숫자·정규화 해시로 고신뢰 중복 그룹 산출, 채널별 헤드라인 인덱스 생성
  → `.state/briefing_index.json` (원문의 1/10 이하)
- `market-briefing/scripts/telegram_digest.py` (기존 유지)

**중간 산출물**
- `.state/market_snapshot.json` — 고정 지표 시세
- `.state/briefing_index.json` — 축약 인덱스 + 고신뢰 중복 그룹
- `.state/topics.json` — 토픽 클러스터 + primary 채널 지정
- `.state/sections/<topic-id>.json` — 섹션 작성 에이전트 산출물

**에이전트 정의 (`.claude/agents/`)**
- `briefing-section-writer.md` — 토픽 1개 담당. 원문 + 관련 지표를 읽고 정리·요약·
  지표·초안 인사이트 작성, 웹 검색으로 최신 확인. `model: sonnet`
- `briefing-reviewer.md` — 섹션 간 잔여 중복·수치 일관성 검수 (조건부 기동)

**스킬 (`.agents/skills/`)**
- `brief/SKILL.md` — 오케스트레이터 본체. 전체 파이프라인 절차와 각 모드의 동작을
  모두 여기에 기술한다.
- `brief-collect/SKILL.md`, `brief-topics/SKILL.md`, `brief-dig/SKILL.md` — 각각
  해당 모드로 진입한다는 것만 명시하고 절차는 `brief`를 참조하는 얇은 스킬.
  (호출 편의를 위해 분리하되, 로직 중복을 막기 위해 본체는 하나로 유지)
- `market-briefing/SKILL.md` (기존) — 주간 마켓브리핑 작성 워크플로. 온디맨드
  브리핑과 목적이 다르므로 유지하되, 1단계 원문 수집에서 `/brief` 산출물을
  참조하도록 갱신한다.

**의존성**
- `market-briefing/requirements.txt`에 `yfinance` 추가 (API 키 불필요)

## CLI 스킬

| 명령 | 동작 |
|---|---|
| `/brief` | 전체 파이프라인 실행 → 대시보드 갱신 |
| `/brief-collect` | 수집만 (텔레그램 + 시세), 합성 없음 |
| `/brief-topics` | 토픽 인덱스만 빠르게 확인 |
| `/brief-dig <토픽>` | 특정 토픽 심층 분석 |

## 기본값

- 오늘 새 글이 없는 채널은 섹션을 만들지 않고 하단에 "오늘 새 글 없음: A, B, C"로
  한 줄 처리한다.
- 토픽은 4~7개 수준으로 묶는다.
- 수치는 `market_snapshot.json`과 원문에 있는 값만 인용하고 생성하지 않는다
  (기존 파이프라인의 "숫자를 지어내지 않는다" 원칙 유지).

## 범위 밖

- 이슈별 동적 종목 차트 (v2)
- 캐싱·증분 클러스터링 (실사용 후 필요 시 추가)
- 유튜브·카카오톡 수집 (사용자가 원문 붙여넣기로 대체)
- 네이버 블로그 자동 게시 (기존 결정 유지 — 사용자가 직접 게시)

## 구축 순서

1. `market_snapshot.py` + `build_index.py` 작성 및 테스트 (파이썬만, 검증 용이)
2. 에이전트 정의 2개 + 오케스트레이터 스킬 작성
3. 대시보드 Artifact 템플릿 작성 및 첫 발행
4. 실사용 피드백 반영 (정보량·레이아웃), 이후 캐싱·증분 클러스터링 검토
